# 一级铁律（四条，优先级最高）

所有 baseline / user 规则都不得与本文件冲突。任务中任何「更优雅的写法」若违反铁律，一律不写。

## 1. 禁止额外编程

**只写当前需求可观察行为所需的代码。**

判定：把某段新增代码（抽象层、配置项、策略分支、工具函数、组件 prop）删掉后，当前需求是否仍能完成？

- 能完成 → 不写。
- 不能完成 → 写，且写到最小形态。

反例：

```ts
// ❌ 需求只要「按 id 查用户」，却预留了缓存策略与重试配置
async function getUser(id: string, opts?: { cache?: boolean; retries?: number })

// ✅ 需求只要查询，就只写查询
async function getUser(id: string)
```

```ts
// ❌ 没有第二个调用方就先抽「通用」层
export function createEntityService(...) { /* 仅 1 处使用 */ }
```

## 2. 不要预想未来

**不为「以后可能」预留接口、配置、目录、依赖。**

判定：

- 是否存在 **2 个真实调用点**？没有 → 不抽共享层。
- 配置项/开关是否有**当前用户可见行为**对应？没有 → 不加。
- 「以后扩展」的目录/文件/类型别名 → 不建。

反例：

```ts
// ❌ 预想以后要支持多主题
type Theme = 'light' | 'dark' | 'auto' // 当前只有 light

// ✅ 当前只有一种，就一种
const theme = 'light'
```

与铁律 1 合并执行：先满足当前需求的最小实现，再用调用点数量决定是否共享。

## 3. 代码整齐

**同一文件、同一目录内，结构稳定、命名一致、同类逻辑同形。**

判定：

- 文件内分区顺序是否与该语言/框架规范一致（如 Vue SFC 七区）？
- 同类函数命名是否同一动词前缀/同一大小写习惯？
- 相邻的两段同职责代码，写法是否同形（不要一段用 early return、一段用深层嵌套表达同一件事）？

反例：

```ts
// ❌ 同一文件三种命名混用
function GetUser() {}
function fetch_list() {}
const handleOk = () => {}
```

```vue
<script setup lang="ts">
// ❌ 状态写在函数之后、import 插在中部（区域混排）
</script>
```

细节见 `readability.md` 与语言级文件（如 `sfc-structure.md`）。

## 4. 中低级可读

**目标读者是中低级开发者：平铺直叙的具名步骤，3 分钟能顺着读完一条路径。**

判定：

- 是否出现炫技链式（>3 层 `.map().filter().reduce()` 嵌套）、过深三元、隐式魔法？
- 关键分支是否有可读的函数名/变量名，而不是靠注释硬撑？
- 新人能否在不问作者的情况下说出「这个函数下一步做了什么」？

反例：

```ts
// ❌ 炫技：可读性差
const ok = a?.b?.map((x) => x.c)?.filter(Boolean)?.reduce((s, x) => s + (x.d ?? 0), 0) > 0

// ✅ 平铺：中低级也能顺着读
const items = a?.b?.map((x) => x.c).filter(Boolean) ?? []
const total = items.reduce((sum, x) => sum + (x.d ?? 0), 0)
const ok = total > 0
```

```ts
// ❌ 魔法：调用方看不懂 3 是什么
setLevel(3)

// ✅ 具名
setLevel(PRIVILEGE_ADMIN)
```

## 冲突裁决

1. 铁律之间若表面冲突，以「当前需求可完成 + 中低级可读」为底线；通常先满足最小实现（1、2），用整齐的形态写出来（3、4）。
2. 任何 baseline 细节规则、user 习惯、第三方「最佳实践」都不得要求你违反铁律。
3. 用户显式要求的非常规写法：先说明与铁律的冲突；用户仍坚持时按用户执行，并在收工汇总里考虑是否记为 user 习惯。
